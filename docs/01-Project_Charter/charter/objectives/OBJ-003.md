# OBJ-003 — Decompor solicitações em tarefas verificáveis

![Tipo: OBJ](../../assets/documentation-style/badges/badge-type-obj.svg) ![Status: refinement](../../assets/documentation-style/badges/badge-status-refinement.svg) ![Versão: v1](../../assets/documentation-style/badges/badge-version-v1.svg)

**Evidência:** `DOCUMENTED` — decisão aprovada pelo responsável pelo projeto; implementação não verificada.

## Motivação

Evitar perda de intenção, ambiguidade e incompatibilidades ao transformar pedidos em funções reutilizáveis e combináveis.

## Resultado esperado

Uma etapa de planejamento com LLM interpreta a solicitação original e a decompõe em tarefas menores, quando necessário, mantendo a finalidade, as restrições e a relação entre as partes. Cada tarefa apresenta propósito, entradas, saídas, dependências e critérios de aceite compreensíveis e verificáveis. Informação insuficiente deve ser identificada, sem inventar parâmetros ou autorizações.

## Critérios verificáveis

- Cada requisito relevante do pedido original pode ser rastreado a uma ou mais tarefas ou a uma justificativa de impossibilidade.
- Cada tarefa possui finalidade, entradas, saídas, dependências e critérios de aceite identificáveis.
- Dependências e compatibilidade de resultados são verificáveis antes da composição.
- Solicitações ambíguas ou incompletas não são convertidas silenciosamente em operações presumidas.
- O plano permite verificar se o resultado composto preserva a finalidade original.

## Limites

Não determina modelo, formato de serialização, sintaxe física de tarefas nem prompt operacional. Essas escolhas pertencem a Scope/Implementation. Casos de teste e metas adicionais permanecem em [OPEN-001](../open-questions/OPEN-001.md).

## Entrada e saída lógicas do planejamento

**Entrada:** solicitação original do usuário, suas restrições e o contexto fornecido. **Saída:** lista de tarefas pequenas e verificáveis ou solicitação de esclarecimento quando faltarem informações. Cada tarefa informa finalidade, entradas e respectivos tipos, saídas e seus tipos, dependências, regras e critérios de aceite. A saída de uma tarefa pode servir como entrada de outra.

O objetivo exige descrição concisa e sem pressupor comandos específicos. Deve preservar a intenção original, sem inventar caminhos, dados ou permissões; tarefas e seus critérios devem permitir à LLM geradora operar com um contexto reduzido. A igualdade para reutilização segue [OBJ-002](OBJ-002.md), comparando propósito e contratos lógicos e não valores concretos.

Os formatos, campos e exemplos a seguir são apenas **candidatos ilustrativos de teste**, sem valor de schema normativo; a decisão técnica fica em [OPEN-003](../open-questions/OPEN-003.md) e Scope/Implementation.

## Exemplo ilustrativo de JSON compacto — saída do planejador

Campos propostos para experimento: `status` = `ok` ou `clarify`; `tasks` lista tarefas com `id`, `goal`, `in`, `out`, `deps`, `rules`, `accept`. As tuplas de `in` têm [nome,tipo,valor] e as de `out`, [nome,tipo]; `@T1.files` significa utilizar uma saída anterior. `file_size[]` nomeia apenas um tipo lógico ilustrativo, ainda sem formato físico.

Solicitação de exemplo: encontrar arquivos `.log` maiores que 10 MiB em `/var/log`, ordenar por tamanho e contar, sem modificar arquivos.

```json
{
  "status": "ok",
  "tasks": [
    {
      "id": "T1",
      "goal": "Listar arquivos .log maiores que 10 MiB",
      "in": [
        [
          "dir",
          "path",
          "/var/log"
        ],
        [
          "min_mib",
          "int",
          10
        ]
      ],
      "out": [
        [
          "files",
          "file_size[]"
        ]
      ],
      "deps": [],
      "rules": [
        "somente leitura",
        "extensão .log"
      ],
      "accept": [
        "somente arquivos regulares",
        "tamanho > 10 MiB"
      ]
    },
    {
      "id": "T2",
      "goal": "Ordenar arquivos pelo tamanho decrescente",
      "in": [
        [
          "files",
          "file_size[]",
          "@T1.files"
        ]
      ],
      "out": [
        [
          "sorted",
          "file_size[]"
        ]
      ],
      "deps": [
        "T1"
      ],
      "rules": [
        "não modificar arquivos"
      ],
      "accept": [
        "ordem decrescente de tamanho"
      ]
    },
    {
      "id": "T3",
      "goal": "Contar arquivos da lista",
      "in": [
        [
          "files",
          "file_size[]",
          "@T1.files"
        ]
      ],
      "out": [
        [
          "count",
          "int"
        ]
      ],
      "deps": [
        "T1"
      ],
      "rules": [
        "somente leitura"
      ],
      "accept": [
        "quantidade igual ao número de itens"
      ]
    }
  ]
}
```

Quando faltar informação indispensável:

```json
{"status":"clarify","questions":["Qual diretório deve ser pesquisado?"],"tasks":[]}
```

Os exemplos não indicam que o modelo tenha sido testado ou que a codificação esteja aprovada.

## Prompt experimental de planejamento — não normativo

```text
Você é um planejador de tarefas Linux.
Converta o pedido em tarefas pequenas, cada uma com uma ação.
Preserve a finalidade e não descreva comandos nem gere Bash.
Use por tarefa: id, goal, in, out, deps, rules, accept.
in = [nome,tipo,valor]; out = [nome,tipo]; deps = IDs anteriores.
rules = restrições; accept = condições verificáveis.
Não invente valores, caminhos, permissões nem dados ausentes.
Retorne somente JSON válido, sem Markdown ou explicações.
Com dados suficientes: {"status":"ok","tasks":[...]}.
Se faltar informação: {"status":"clarify","questions":["pergunta objetiva"],"tasks":[]}.
Solicitação: Encontre os arquivos .log maiores que 10 MiB em /var/log, ordene-os do maior para o menor e informe a quantidade. Não modifique nenhum arquivo.
```
